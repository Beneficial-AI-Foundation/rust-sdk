**Design choices (drafter defaults, for the spec owner).**

1. *Expected-result definitions instead of a `match` over the result.* E09/E10/E11 compare the
   result with `openRs1`/`openRs2`/`openAt` in `Defs`, which encode the Section 3 lists step by
   step on byte lists (`components`, `b64Decode`, `strOfBytes?`, `lookupKey`, `hmacSha256`,
   `transcriptV1/V2`, `bodyExpiry`, `Expired`). A `match result with` per error (the E01–E04
   form) would need, for each of 5 (E09) and 11 (E10) error arms, the conjunction of all earlier
   checks passing. The definitions follow the plan's ordered list; they do not follow the
   translated loops or monadic plumbing, but they are close to the Rust control flow, which a
   reviewer may count as "mirroring".
2. *Weakest codec-state hypothesis.* E09/E11 take only `CodecFallbacksKnown` (every rs1 fallback is
   a key id), E09a only `FallbacksKnown`, E10 none. This deviates from the style guide's "a single
   hypothesis `(h : self.Valid)`" and from the lead's instruction to state the codec-state predicate
   as a hypothesis of E09/E10. Reason: E10 cannot panic on any codec (the lookup returns an
   `Option`), and HMAC accepts keys of any length, so the other clauses are not needed.
   `CodecValid → CodecFallbacksKnown` is immediate, so round trips stated with `CodecValid` can use
   these theorems directly.
3. *Single-key codecs and `CodecValid`.* `CodecValid` puts no constraint on a single-key codec,
   because `new_unchecked` (lines 286–290) and the deprecated `new` (line 278) accept a key of any
   length. Plan §4 says "every key is at least 32 bytes" and "the constructors enforce these", which
   holds only for keyring codecs and `try_new`. `CodecValid` also requires pairwise distinct key ids
   (the Rust `HashMap` invariant that the translated `HashMap` does not carry), which plan §4 does
   not list.
4. *Transcript domains stated on the decoded components* (revised in fix round 2, finding F1;
   until then the bound was stated on the encoded components). `h_len` of E09 (and `h_len1` of
   E11) is `∀ b t body, components sealed = [versionV1, b, t] → b64Decode b = some body →
   (transcriptV1 ad body).length ≤ Usize.max`; `h_len` of E10 (and `h_len2` of E11) is
   `∀ k b t kid body, components sealed = [versionV2, k, b, t] → b64Decode k = some kid →
   b64Decode b = some body → (transcriptV2 kid ad body).length ≤ Usize.max`. These are exactly
   the W10/W11 domains at the transcripts the code builds (request_state.rs lines 623, 627 and
   672, 683, 687–688). The encoded-component bound implies the decoded one
   (`b64Decode_length_le`), so the revised theorems are strictly stronger (checked in scratch,
   below). The revision matters for composition: at a token produced by E07/E08 the decoded body
   (and kid) is the sealed one (`b64Decode_b64`), so the premise reduces to E07/E08's own `h_len`,
   while the encoded bound would need an extra premise on the length of `b64 body`. The premise is
   stated only for tokens of the right shape whose components decode, so it is weaker than a
   bound on the whole input such as `|sealed| + |ad| + 42 ≤ Usize.max`. It is still not the
   exact weakest condition: it is also required for tokens that fail between the decoding and
   line 627 (E09: no fallback, tag not Base64) or 687 (E10: lines 673–680, 684).
5. *`h_count` kept separately* (W06/W08/W09 domain `count dot < Usize.max`). It cannot be derived
   from the input: a `Slice` gives only `count ≤ length ≤ Usize.max`. *Qualified in fix round 3
   (G3):* this holds for E09 and E10 only. Since fix round 2 (finding F2) E11 has no `h_count`:
   on its E09/E10 branches the token starts with `"rs1"` or `"rs2"`, so it contains a byte that
   is not `.` and the count is derivable. This departs from plan §3 "Lean-model domains"; open
   question (j).
6. *Seal outputs as UTF-8 bytes* (`ExtModel.utf8 result = …`), not as Lean `String` equality.
   `utf8_inj` makes them equivalent. The tag length is the literal `32` (`[u8; 32]`); `Defs` has no
   `TAG_LEN`.
7. *E07/E08 domains are exact.* Overflow anywhere in the capacity sum (`usize` addition or E02),
   or a capacity above `isize::MAX` (`String::with_capacity`), fails. Every later push stays within
   that capacity because `(b64 x).length ≤ b64Len x.length`. No UTF-8 premise on the E08 kid: the
   kid is used only through `as_bytes`/`len` and Base64. *Qualified in fix rounds 2 and 3 (F3,
   G1):* "exact" means exact for the Lean model, and only sufficiency is what the theorems state
   (and the scratch round trips use); necessity is argued in the docstrings, not proved. The
   model domain is also larger than the Rust no-panic domain, by the stated exceptions of plan §4
   "Unlimited memory" and of the size convention of `trusted/Rmcp/FunsExternal.lean`: a
   transcript `Vec` above `isize::MAX` bytes, and HMAC SHA-256 on a message of at least
   `2^61 − 64` bytes or a key of at least `2^61` bytes (bit-length overflow, a panic under
   `overflow-checks`), succeed in the model and panic in Rust.
