## Charon settings

`[package.metadata.charon]` was added to `crates/rmcp/Cargo.toml` verbatim from plan Section 9.
Key names checked against the pinned Charon (`charon/src/bin/charon/toml_config.rs` at
`f5208b1c`): `start_from`, `hide_marker_traits`, `exclude`, `opaque` are fields of `TomlConfig`,
with the same names as the CLI options; no difference from the plan. `TomlConfig` has further
fields that widen the translation: `extract_opaque_bodies`, `start_from_if_exists`,
`start_from_attribute`, `start_from_pub`, `include` and `rustc.flags` (appended to
`rustc_args`). Notes:

- Charon reads `./Cargo.toml` of the working directory, so the script runs it in
  `.llbc/work/crates/rmcp`.
- `TomlConfig` does not deny unknown keys, so a misspelt key would be ignored silently. Before
  Charon runs, the translate script reads `[package.metadata.charon]` with `cargo metadata`
  and fails unless its keys are a subset of {`start_from`, `hide_marker_traits`, `exclude`,
  `opaque`}, the three lists are present, non-empty lists of strings, and
  `hide_marker_traits` (if present) is a boolean.
- After Charon, it fails unless the options recorded in the LLBC (`translated.options`) have
  `start_from`, `opaque`, `exclude` equal to those lists, and `rustc_args == []`,
  `include == []`, `start_from_if_exists == []`, `start_from_attribute == []`,
  `extract_opaque_bodies == false`, `start_from_pub == false`; and unless the LLBC target
  information (`translated.target_information`, a list of `{key: <triple>, value: …}`) has
  exactly the keys `["x86_64-unknown-linux-gnu"]`. Field names checked in the LLBC of the
  scratch run (Charon 0.1.235). The flag fallback was not needed.
- `hide_marker_traits = true` is redundant with `--preset=aeneas`, which already sets it; harmless.

### `lake build --wfail` and the Aeneas library (B10)

With the pinned rev, the Aeneas Lean library itself contains four `sorry`s:
`Aeneas/Std/Slice.lean:363` (`core.slice.Slice.get_unchecked`), `:586`
(`get_unchecked_SliceIndexUsizeSlice_spec`), `Aeneas/Std/StringIter.lean:12` and `:15`
(`IteratorChars.next`, `IteratorChars.collect`). Lake replays their warnings on every build, and
`--wfail` counts replayed warnings of dependencies ("Some required targets logged failures:
Aeneas.Std.Slice, Aeneas.Std.StringIter"). Lake 4.31 has no per-package fail level.

Resolution (human decision in the fix round): every library in `formal/lakefile.toml` sets
`leanOptions = { warningAsError = true }`, and `lean-build.yml` runs a plain `lake build`.
Checked on a scratch copy: a module with `theorem … := sorry` imported from `Proofs.lean` fails
the build (`error: … declaration uses 'sorry'`), a file in `specs/Drafts/` is not built, and the
Aeneas warnings no longer fail it. Neither the generated translation nor any target uses
`get_unchecked` or `IteratorChars`.

A theorem that came to depend on those Aeneas `sorry`s would build without any warning (the
`sorry` is in a dependency). It is caught only where its axioms are printed: a theorem
restated with `recall` in a spec file under a `#guard_msgs` `#print axioms` check would show
`sorryAx` there and fail. Lemmas and models that are not recalled in a spec file are not
covered; see Open items.

`warningAsError` can be switched off inside a file (`set_option warningAsError false`, or
`… in`), after which `sorry` builds with exit 0 (checked: scratch copy, `lake build` exit 0,
`warning: proofs/Proofs/Bad.lean:3:8: declaration uses 'sorry'`). CI therefore runs
`scripts/lean-guard.sh` (fix round, T2 below).

### T2: CI guard (`scripts/lean-guard.sh`, steps in `lean-build.yml`)

(a) `lean-guard.sh sources`: fails if a `.lean` file under `formal/specs` (except
`formal/specs/Drafts/`), `formal/proofs` or `formal/trusted` contains, as a whole word
(`grep -wE`), `warningAsError`, `sorry`, `admit`, `native_decide`, `bv_decide`, `skipKernelTC`
or `set_option linter.<name> false`; and if a `.lean` file under `formal/translation` contains
any of these except the linter options (Aeneas emits `set_option linter.dupNamespace false`,
`linter.hashCommand false`, `linter.unusedVariables false` in every generated file). It also
fails unless every `[[lean_lib]]` in `formal/lakefile.toml` has
`leanOptions = { warningAsError = true }` and none sets `moreLeanArgs`/`weakLeanArgs`.

Comment rule: the match is textual, so the banned words are banned in comments and docstrings
too (write "placeholder" or "unproved"). A Lean-aware filter would have to parse nested
`/- -/` comments and strings; a false positive costs a rewording, a false negative a hidden
`sorry`. `sorryAx` (as in an expected `#print axioms` message) is a different word and does not
match. Non-`.lean` files (patches, evidence) are not scanned.

(b) `lean-guard.sh build-log build.log`, after `set -o pipefail; lake build 2>&1 | tee build.log`:
fails if a `warning:` line names a file under `proofs/`, `specs/`, `trusted/` or `translation/`
(Lake prints our files relative to `formal/`, e.g. `warning: proofs/Proofs/Bad.lean:3:8: …`;
the replayed Aeneas lines are `warning: Aeneas/Std/…`), or if the log is missing or empty.
