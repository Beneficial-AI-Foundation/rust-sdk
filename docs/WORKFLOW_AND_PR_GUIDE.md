# Operational Workflow

This guide covers the formal verification work in this fork of the Rust MCP SDK: the Lean project
in `formal/`, the scripts under `scripts/`, the Charon settings in `crates/rmcp/Cargo.toml`, and the
status records under `formal/docs/`. The process follows [`VERIFICATION.md`](VERIFICATION.md); the
scope, targets, steps, and status vocabulary are defined in the
[master plan](MCP_SDK_Verification_Master_Plan_EN.md). Ordinary SDK changes follow the
[contribution guide](CONTRIBUTE.MD). See also the [style guide](STYLE_GUIDE.md), the
[reviewer guide](REVIEWER_GUIDE.md), and the [AI review questions](AI_PR_REVIEW_QUESTIONS.md).

The older extraction under `verification/host_origin/` keeps its own README and its recorded hand
edit; it is not part of `formal/` and the rules below do not apply to it retroactively.

## Process

Work runs in three phases (plan Section 8, "Process"):

1. **Phase A, once for the whole crate:** scope, translate, review the trusted part of the
   translation (exclusions, opaque items, patches, external axioms), turn on CI.
2. **Phase B, per function, pipelined in call-graph batches:** spec draft, at least two
   independent agent reviews, human sign-off, proof, restated `theorem` in the spec file.
3. **Phase C, once after every proof is checked:** proof refinement with spec statements frozen.

A proof starts only after its own spec is signed off, and after the axioms it uses are signed off.

## Layout

```
crates/rmcp/Cargo.toml     [package.metadata.charon]: start_from, exclude, opaque
scripts/                   aeneas-install.sh, apply-patches.sh, aeneas-translate.sh,
                           llbc-dir-guard.sh (work-directory guard),
                           lean-guard.sh, lean_guard.py, lean-axiom-audit.lean (CI guard)
formal/
  lakefile.toml            pins Aeneas (single source of truth for the toolchain)
  docs/                    STATUS.md, board.yaml, functions/, evidence/, blockers/, the pilot record (removed from git history on 2026-11-23),
                           the pilot record (removed from git history on 2026-11-23) (copied pilot artifacts, never built)
  trusted/                 patches/, Rmcp/{Types,Funs}External.lean, evidence/   READ ALL OF IT
                           aeneas-bundle.sha256 (digests of the Aeneas release assets),
                           axioms.lock (trusted axioms), native-axioms.lock (accepted
                           native-code axioms: Aeneas toStr side conditions)
  specs/                   Defs/, Specs/ (spec files), Drafts/ (not built)    READ ALL OF IT
  translation/             generated by Aeneas, never edited
  proofs/                  Proofs/ (Proofs/External/: laws of the models)    checked by Lean
```

An auditor reads all of `formal/trusted/` and `formal/specs/`, and none of `formal/translation/`
(regenerated and checked by CI) or `formal/proofs/` (checked by Lean).

## Do not Modify Generated Files

**Never edit** anything under `formal/translation/` by hand (`Rmcp/Types.lean`, `Rmcp/Funs.lean`,
`translation.json`; Aeneas generates no `Rmcp.lean`). There are no exceptions: the translation CI
regenerates them and fails on any difference. To change them, change one of:

- the Rust source (its own PR; see below),
- a translation patch in `formal/trusted/patches/`,
- the Charon settings in `crates/rmcp/Cargo.toml`,

and re-run `scripts/aeneas-translate.sh`. Commit the regenerated output together with the change
that produced it.

`formal/trusted/Rmcp/TypesExternal.lean` and `FunsExternal.lean` are started once from the
generated `*External_Template.lean` files (git-ignored, next to `Funs.lean`) and then maintained by
hand; see [External functions and axioms](#external-functions-and-axioms). The templates contain
`set_option linter.dupNamespace false`, `linter.hashCommand false` and
`linter.unusedVariables false`, which `scripts/lean-guard.sh sources` rejects in `trusted/`;
remove these lines when starting the externals from the templates (lead decision, S04a).

**Never change** production code in `crates/rmcp/src/model/request_state.rs` or
`crates/rmcp/src/model/request_state_wire.rs` as part of a verification PR. The only exceptions
are:

- the reviewed `request_state_wire` refactor of plan Section 9, landed as its own PR (plan step
  S04a), and
- new Rust tests inside either file's private `mod tests` (plan step S16).

A source change changes the translation; the translation CI forces the regenerated files into the
same PR, and the Lean build re-checks every proof against them.

## When translation fails

Do not work around a translation problem in generated Lean. For each error or skipped item:

1. **Out of scope:** add it to `exclude` in `[package.metadata.charon]`, with a comment giving the
   reason. Nothing verified may depend on an excluded item.
2. **In scope:** write a translation patch (below), or fix the problem upstream in Charon or
   Aeneas. For new public wire functions, prefer following the Aeneas-safe coding rules of plan
   Section 2.1 in the source itself.
3. **Last resort:** `opaque`, only when the item cannot be translated and there is no useful Rust
   model to patch in. Its behaviour then becomes an axiom in `FunsExternal.lean`, so it needs a
   strong justification and the same review as an axiom.

If no change within the project's scope resolves the blocker, record it in
`formal/docs/blockers/Sxx.md` with a minimal reproducer. Excluding a target from the project needs
the user's decision (plan Section 2.3).

Check after every run that every target appears in `Funs.lean` with a real body. To learn how
Aeneas translates Rust into Lean, see the
[Aeneas documentation](https://github.com/AeneasVerif/aeneas/tree/main/documentation).

### Translation patches

A patch is a small, behaviour-preserving edit applied only to the copy of the crate in
`.llbc/work/`; the real source is never patched. None are planned (plan Section 4, "What must be
trusted"). If one is needed:

1. Run `scripts/apply-patches.sh` so that `.llbc/work/` holds the patched copy.
2. Make the edit in `.llbc/work/`.
3. Save it with `git diff` as `formal/trusted/patches/NN-short-name.patch`, with the header
   `VERIFICATION.md` §4 requires: the change, why it is needed (with the upstream issue, if any),
   and why the behaviour is unchanged.
4. Re-run the translate script and check that the item now translates.

One concern per patch. Each patch is reviewed like an axiom (see
[Review and sign-off](#review-and-sign-off)), and every target whose translation depends on it is
`linkage: PATCHED`. Delete a patch when an Aeneas upgrade makes it unnecessary.

## Pinned toolchain

The only pin is the Aeneas release tag in `formal/lakefile.toml` (at the time of writing
`nightly-2026.08.20-5d08da4`). `scripts/aeneas-install.sh` reads it and installs the matching
Charon, Aeneas, Rust nightly and Lean toolchain; do not install them any other way. Changing the
`rev` is its own PR. That PR re-runs both scripts, re-translates all targets, rebuilds all proofs,
and records the result in an evidence file.

`formal/trusted/aeneas-bundle.sha256` holds the committed sha256 of every Aeneas release asset
used: the release bundles and the `lean-build-aeneas` Lean-library archives, keyed by
`<tag>/<asset>`. `scripts/aeneas-install.sh` verifies the downloaded bundle against it, and
`scripts/lean-guard.sh aeneas-archive` verifies the archive Lake fetched; both fail on a mismatch
or a missing entry. A `rev` bump PR adds the new tag's entries to that file.

The Lean dependencies are pinned by commit in `formal/lake-manifest.json`, and
`scripts/lean-guard.sh sources` fails unless it lists exactly the ten recorded packages at their
recorded commits (`MANIFEST_PACKAGES` in `scripts/lean_guard.py`): Aeneas at
`5d08da45a405913bbee6fd544e01debf8154ac9d`, with `url`, `inputRev` and `subDir` equal to the
lakefile's `git`, `rev` and `subDir`; Mathlib at `fabf563a7c95a166b8d7b6efca11c8b4dc9d911f`
(`v4.31.0`); and the eight packages Mathlib brings in. A `rev` bump PR updates that list too.

The Rust toolchain is checked where it is used: `scripts/aeneas-translate.sh` sets
`RUSTUP_TOOLCHAIN` to the bundle's channel and requires the `rustc` that cargo runs to report, in
`rustc -vV`, commit-hash `14210df0e27ccd7d9e6a05b8085cbd438e4bbc65`, commit-date `2026-05-31` and
release `1.98.0-nightly` (nightly-2026-06-01), and `charon toolchain-version` to print the
bundle's channel. `RUSTUP_HOME` is allowed (container images set it); every other `RUSTUP_*` is
refused. A fake `rustc` that prints exactly these lines is not caught by this check.

The dependency versions that the axioms rely on are pinned in `scripts/aeneas-translate.sh`
(`hmac 0.13.0`, `sha2 0.11.1`, `base64 0.23.1`). The script runs one `cargo tree` over the whole
dependency tree of `rmcp` in the translated configuration and fails if any dependency does not
come from crates.io (path, git or other registry) or if one of these three resolves to another
version. `Cargo.lock` is git-ignored in this repository and never copied into `.llbc/work/`, so
the dependencies are resolved afresh on every run and this check is what catches drift.

The translate script also pins `crates/rmcp/build.rs` by sha256 (`BUILD_RS_SHA256`). A PR that
changes `build.rs` must update that digest in `scripts/aeneas-translate.sh` in the same PR, after
checking that the build script still emits nothing (no `cargo:` directive).

## Translating

From the repository root:

```bash
scripts/aeneas-install.sh      # once, and after bumping the Aeneas rev
scripts/aeneas-translate.sh    # after any change to src/, patches, or Charon settings
```

The translate script fixes the configuration (`x86_64-unknown-linux-gnu`,
`--no-default-features --features request-state --lib`), with overflow checks and debug
assertions pinned on: every cargo call, also through Charon, gets
`--config profile.dev.overflow-checks=true --config profile.dev.debug-assertions=true`. The proofs
hold only for that configuration. So that nothing else changes the build, the script refuses to
run with an environment variable that changes how cargo or rustc build (`RUSTFLAGS`, `RUSTC*`,
`RUSTDOC*`, `CHARON_*`, `AENEAS_*`, and every `CARGO_*` except `CARGO_HOME`, `CARGO_TARGET_DIR`,
`CARGO_TERM_*`, `CARGO_NET_*`, `CARGO_HTTP_*`, `CARGO_INCREMENTAL` and
`CARGO_REGISTRIES_CRATES_IO_PROTOCOL`, and every `RUSTUP_*` except `RUSTUP_TOOLCHAIN` and
`RUSTUP_HOME`), with a selected `rustc` that is not the pinned nightly (see
[Pinned toolchain](#pinned-toolchain)), with a `.cargo/config` or `.cargo/config.toml` in the
source, the work copy or any ancestor of it, or with `[profile]`, `[patch]`, `[replace]` or
`cargo-features` in the workspace or `crates/rmcp` manifest. It runs cargo with an isolated
`CARGO_HOME` (no configuration file, only the registry and git caches), and it fails if a
dependency of `rmcp` does not come from crates.io, if the build script is not the pinned
`crates/rmcp/build.rs` or emits anything, on a nonzero Charon or Aeneas exit, Charon options in the
LLBC that differ from or widen the settings, a missing target, any `sorry` in the generated files,
or a dependency version mismatch. The exact lists are in `formal/README.md` ("Translated
configuration") and the header of `scripts/aeneas-translate.sh`.

Aeneas writes into the scratch directory `$RMCP_LLBC_DIR/out` (default `.llbc/out`); only after
the output checks pass does the script copy it to `formal/translation/` (or
`$RMCP_TRANSLATION_DEST`) with `rsync -a --delete --checksum`, refusing a destination that holds
anything other than an earlier output (`Rmcp/`, `translation.json`). The work directory gets
`rsync --delete` (`work/`) and `rm -rf` (`out/`, `cargo-home/`), so `scripts/llbc-dir-guard.sh`
(used by both scripts) refuses an `RMCP_LLBC_DIR` that is `/`, `$HOME`, the repository or contains
one of them, contains or lies inside the source (except `<source>/.llbc`), has a symlinked
`work/`, `out/`, `cargo-home/` or `target/`, or exists, is not empty and has no marker file
`.rmcp-llbc-dir` (written into every work directory it accepts; the repository's own `.llbc` is
accepted without it). For a scratch run, set `RMCP_SOURCE_ROOT`, `RMCP_LLBC_DIR` and
`RMCP_TRANSLATION_DEST` together and use a new or empty work directory (`formal/README.md`,
"Commands").

## Library roots

`formal/specs/Defs.lean`, `formal/specs/Specs.lean`, and `formal/proofs/Proofs.lean` are maintained
by hand and list only accepted modules:

- add a module to `Defs.lean` when its definitions are signed off;
- add a proof module to `Proofs.lean` when its proof is complete;
- add a statement to a spec file under `Specs/` (as a `theorem Theorems.…` proved by the spec theorem, with its `#guard_msgs` axiom check)
  only when its proof is complete and its spec is `REVIEWED`.

Statements awaiting proofs stay in `formal/specs/Drafts/`, which belongs to no library and is never
built. A proof with `sorry` is never merged: every library sets `warningAsError`, and CI fails on
any warning in this project's files (see [Building and Checking](#building-and-checking)). The
import rules are in [Library layering](STYLE_GUIDE.md#library-layering).

## Building and Checking

```bash
cd formal
../scripts/lean-guard.sh sources            # lakefile, manifest pins, banned words and constructs
lake exe cache get
set -o pipefail; lake build 2>&1 | tee .lake/build.log    # .lake/ is git-ignored
../scripts/lean-guard.sh build-log .lake/build.log  # only the four recorded Aeneas warnings
../scripts/lean-guard.sh axioms             # only after a successful build: axioms, kernel replay
../scripts/lean-guard.sh aeneas-archive     # Aeneas archive and installed build match the digest
```

The build gate (human decision, S03): every `[[lean_lib]]` in `formal/lakefile.toml` sets
`leanOptions = { warningAsError = true }`, so a plain `lake build` fails on any warning in this
project's modules, including `sorry`, and runs the `#guard_msgs` checks. `lake build --wfail` is
not used: the pinned Aeneas Lean library has four `sorry` warnings
(`Aeneas/Std/Slice.lean:363,586`, `Aeneas/Std/StringIter.lean:12,15`) that Lake replays on every
build, so `--wfail` can never pass (the S03 evidence (git history at 01bdc9b)). The gate can return to
`--wfail` once an Aeneas bump removes them. Because a file can switch `warningAsError` off, hide
messages, add declarations without a kernel check, or run code during the build,
`scripts/lean-guard.sh` adds these checks (implemented in `scripts/lean_guard.py`, run with
`python3 -I`, Python 3.11 or later, and `scripts/lean-axiom-audit.lean`):

- `sources`: `formal/lakefile.toml` must have exactly the five libraries of plan Section 5 with
  their fixed `srcDir` and roots, each with exactly the keys `name`, `srcDir`, `roots`,
  `leanOptions`, and `leanOptions` exactly `{ warningAsError = true }`; the package may set only
  `name`, `defaultTargets` (including `Defs`, `Proofs`, `Specs`), one `[[require]]` (aeneas) and
  the libraries; `formal/lakefile.lean` must not exist. `formal/lake-manifest.json` must list
  exactly the recorded packages at their recorded commits
  (see [Pinned toolchain](#pinned-toolchain)).
  Every hand-written `.lean` file under `formal/` (all except `.lake/`, `specs/Drafts/` and
  `translation/`) fails on the whole words `warningAsError`, `sorry`, `sorryAx`, `admit`,
  `native_decide`, `bv_decide`, `skipKernelTC`, `proofAsSorry`, `implemented_by`, `extern`,
  `unsafe`, `ofReduceBool`, `ofReduceNat` and `trustCompiler`, on the `native` option of `decide`
  (`+native`, `-native`, `native :=`), on `set_option linter.<name> false` (in `trusted/` too),
  and, outside `trusted/`, on `axiom`. In `proofs/`, `specs/` and `trusted/` alike it also fails
  on anything that runs or registers a metaprogram during the build: `#eval`, `#exit`, `run_cmd`,
  `run_tac`, `run_elab`, `run_meta`, `elab`, `elab_rules`, `initialize`, `builtin_initialize`,
  `macro`, `macro_rules`, `syntax`, `simproc` and its variants, `register_option`,
  `register_simp_attr`, `declare_syntax_cat`, `addDecl`, `addAndCompile`, `modifyEnv`, `setEnv`,
  `withOptions`, the metaprogramming types (`IO`, `CoreM`, `MetaM`, `TermElabM`, `TacticM`,
  `CommandElabM`, ...), `Lean.Elab`, any `debug.` option, and the attributes that register a
  metaprogram (`command_elab`, `term_elab`, `tactic`, `init`, `builtin_*`, `delab`, `app_delab`,
  `simproc`, `env_linter`, code actions, `widget_module`); the full list is in
  `formal/README.md`. `macro` and `syntax` are banned because a macro can produce any command
  without writing its keyword; `notation`, `infix`, local instances and `simp` attributes are
  allowed. Write a custom tactic out inline; a separately reviewed tactic module would be a human
  decision (lead decision 2026-11-22: the ban stays everywhere). The match is textual, so
  comments and docstrings count (write "assumption", "placeholder", "grammar", "set up",
  "input/output" instead of the banned words in prose). `#guard_msgs` is allowed only in
  `specs/Specs.lean` and `specs/Specs/`, and only as a bare `#guard_msgs in` followed, on the same
  or the next line, by exactly one `#print axioms <name>` that ends the line (no options, no
  `drop`). Written in backticks on both sides (`` `#guard_msgs` ``) it is prose and skipped; this
  exemption covers only `#guard_msgs`, not the banned words. Generated files in `translation/`
  get the same word, `native` and metaprogramming rules; `#guard_msgs` is banned there, Aeneas's
  `set_option linter.* false` is allowed, and `axiom` is banned except in the unbuilt
  `*_Template.lean` files, which are exempt. Symlinks under `formal/` fail.
- `build-log`: an exact allowlist. The log must have a `Build completed successfully` line, and
  every line containing `warning:` or `error:` must be exactly one of
  `` warning: Aeneas/Std/Slice.lean:363:4: declaration uses `sorry` `` and the same text for
  `Aeneas/Std/Slice.lean:586:8`, `Aeneas/Std/StringIter.lean:12:4` and
  `Aeneas/Std/StringIter.lean:15:4`.
- `axioms` (only after a successful `lake build`): fails if `formal/.lake/build/lib/lean` holds
  anything but modules named `Rmcp`, `Defs`, `Proofs`, `Specs` or below them. It runs
  `lean-axiom-audit.lean` with the toolchain's own `lean`, not `lake env`, with an explicit
  `LEAN_PATH` (toolchain library first, then the manifest's packages, then the project build) and
  no dynamic-loader variables. The audit imports the roots of the default-target libraries
  without running any code of the imported modules (`loadExts := false`) and fails if a project
  `.olean` is stale (the source hash in its Lake `.trace` file differs from the current source's);
  if the constants declared in the project modules that the roots reach depend (one
  order-independent walk over all of them through types, values and whole inductive blocks, a
  superset of what `#print axioms` reports) on an axiom other than `propext`,
  `Classical.choice`, `Quot.sound`, those declared in the `RmcpExternal` roots
  (`Rmcp.TypesExternal`, `Rmcp.FunsExternal`) and the native-code axioms that are the Aeneas
  `toStr` side condition of a string literal declared in `Rmcp.Types` or `Rmcp.Funs` (nothing
  else native), which catches `sorryAx` (also when inherited from the Aeneas library or hidden
  from the log) and the `<decl>._native.*` axioms of `native_decide`/`decide +native`; if an `RmcpExternal`
  root declares a constant in the namespace `rmcp` or adds an alias (`export`); or if the kernel
  rejects a project constant when every project constant is replayed
  (`Lean.Environment.replay`, as `leanchecker` does) onto the non-project modules they import,
  which catches declarations added without a kernel check and altered `.olean` files. Then the
  locks (audit scope: human decision 2026-11-23 for `axioms.lock`, applied by the lead to
  `native-axioms.lock`): every trusted axiom (`RmcpExternal` roots) and every native-code axiom
  reachable from some constant declared in a `Defs`, `Proofs` or `Specs` module (every constant
  of such a module counts, including private helpers, instances and auxiliary declarations),
  transitively through any constant including the generated `Rmcp.Types`/`Rmcp.Funs`
  definitions (the same walk), must be in `formal/trusted/axioms.lock` or
  `formal/trusted/native-axioms.lock` with its statement hash (and module, for native ones);
  axioms no such constant depends on are listed for information and need no entry, so importing
  `Rmcp.Funs` into a proof does not require locking every placeholder external. A lock entry for a
  declared but unused axiom is reported as "unused (allowed)" (a reviewed model may be locked
  early); an entry for an axiom that is no longer declared, or whose statement hash differs, fails.
  The statement of a declared axiom that is neither locked nor used (today all 41 placeholder
  externals) is not checked: it can change or vanish in any PR without CI failing, so reviewers of
  `trusted/` read such changes in the source diff. Only the import closure of the default-target
  roots is audited: the namespace check and the locks cover `Rmcp`/`RmcpExternal` once a
  `Defs`/`Proofs`/`Specs` module imports `Rmcp.Funs` (S06) or they become default targets (a
  lakefile change by the lead; unused placeholders no longer block it).
- `aeneas-archive`: fails if an Aeneas Lean-library archive Lake fetched does not match
  `formal/trusted/aeneas-bundle.sha256`, if the installed Aeneas build and the archive do not hold
  the same regular files with the same bytes (every file except `*.hash` and `*.trace`), or if
  the library is built without an archive (unless `LEAN_GUARD_AENEAS_FROM_SOURCE=1` marks a build
  from the pinned sources).
- `unpack-build TAR`: used by CI only (below).

Limits: the `sources` rules are textual, not semantic, and the metaprogramming list is defence in
depth, not complete, so reviewers check for metaprogramming. Only the axioms declared in the
`RmcpExternal` roots are trusted by the audit, so those files still need review. A module that no
root imports is neither built nor audited. Unlike `#print axioms`, the audit does not lose axioms
on inductive/constructor cycles: it follows types, values and whole inductive blocks with one
visited set (an over-approximation).

For Rust-side changes:

```bash
cargo test -p rmcp --no-default-features --features request-state --lib
cargo clippy -p rmcp --no-default-features --features request-state --lib -- -D warnings
just fix                   # fmt and clippy fixes, see CONTRIBUTE.MD
```

CI runs three workflows on every relevant PR: the translation is not stale
(`aeneas-translation.yml`), the Lean project builds (`lean-build.yml`), and the patched copy passes
the crate's tests (`patched-tests.yml`). A PR is ready only when all three pass.

`lean-build.yml` has two jobs, because `lake build` elaborates the project, and elaboration runs
code that could rewrite files of the runner (a `#eval` rewriting `scripts/lean-guard.sh`, say)
before a later step of the same job:

- `build`: checkout, a pinned elan binary checked by sha256, `lean-guard.sh sources` before any
  Lean code of the project runs, `lake exe cache get`, `lake build` (with `pipefail`, tee'd to
  `.lake/build.log`), then `.lake/build` and the log packed into one tar file and uploaded. Only
  this job restores the `formal/.lake/packages` cache; `formal/.lake/build` is never cached.
- `check` (`needs: build`): a fresh runner and checkout, so the scripts come from git; the pinned
  elan installed afresh; `sources` again; the Mathlib cache and the Aeneas release archive fetched
  afresh with no cache (`lake exe cache get`, `lake build Aeneas`) and `aeneas-archive`; then the
  artifact is unpacked with `lean-guard.sh unpack-build` (only `build/` and `build.log`, no links,
  no absolute or `..` paths) and `build-log` and `axioms` run. No Lake command runs after the
  unpack, and the audit runs no code from the `.olean` files, so no project code runs in this job.

What remains (`formal/README.md`, "What CI checks"):

- The artifact is attacker-controlled data if the build ran malicious code. Job `check` replays
  it in the kernel and audits its axioms, but cannot tell whether it was compiled from these
  sources: a build that runs code could upload output of a different (or empty) project. The only
  barrier is that the build runs no project code: the metaprogramming bans of `sources`, checked
  in job `build` before the build, and review.
- The `.olean` files are memory images that Lean maps without validating them. A crafted file
  could crash the audit or worse; job `check` has read-only repository permissions and no
  secrets, so the worst outcome is a wrong check result.
- The Mathlib oleans come from Mathlib's cache server and are not checked against a committed
  digest (an open scope question for the human).
- On the translation side, a fake `rustc` that prints exactly the pinned `rustc -vV` lines is not
  caught by asking it (see [Pinned toolchain](#pinned-toolchain)).

## Status Records and Evidence

Every PR that advances a plan step updates the records under `formal/docs/` in the same PR:

- `board.yaml`: task state (`NOT_STARTED`, `IN_PROGRESS`, `ACCEPTED`, `BLOCKED`, `DEFERRED`);
- `functions/<ID>.yaml` (`W01`–`W15`, `E01`–`E11`, `E09a`): the four independent fields
  `translation`, `spec`, `linkage`, and `proof`, plus `spec_drafted_by`, `spec_reviews`, and
  `spec_owner`;
- `evidence/Sxx.md`: exact commands, exit status, the Aeneas tag and commit translated, axioms
  added or changed, AI-drafted or AI-reviewed artifacts (tool and model), and the reviewer
  decision;
- `blockers/Sxx.md`: written on failure, with a minimal reproducer;
- `STATUS.md`: the trusted-base section whenever an axiom, patch, exclusion, or opaque item
  changes.

Only a human may set `spec: REVIEWED` or move a task to `ACCEPTED`; see
[AI contributions](#ai-contributions). A deadline never changes a status.

## PR Workflow and Formatting

All verification PRs must advance a step (`Sxx`) of the master plan, or close an open issue in the
project, unless special circumstances are justified.

Whenever possible, a PR should cover exactly one step and one function (`Wxx` or `Exx`). Keep its
scope as small as possible, ideally not exceeding ~500 LOC of hand-written Lean and Rust.
Regenerated translation output, refactoring, and documentation do not count towards that limit.

Keep these kinds of change in separate PRs:

- a source refactor or Aeneas `rev` bump,
- a change to the Charon settings or a translation patch, with the regenerated translation,
- an external axiom or model,
- a specification,
- a proof of an already signed-off specification.

A specification and its proof may share a PR only if the specification is signed off first; see
[Specifications before proofs](#specifications-before-proofs).

Discuss with the others working on the project before starting a PR, to avoid duplicate work.
The board in `formal/docs/board.yaml` records who owns each task.

PRs are reviewed when marked as ready (i.e., not a draft) and all checks have passed. After the PR
is created (or marked as ready), hold off on meaningful changes until after the review, so that
reviewers do not look at outdated code. After review the author is responsible for merging the
accepted PR, and is expected to do so promptly.

The expected format for PR title, body, and footer is:

**Title format:** verification PRs name the step, function ID, and Rust function, for example
"S07 E01: specify and prove `open_authenticated_body` in `request_state.rs`". Other PR titles use
imperative present tense ("add" not "added") and no trailing period.

**Body format:**

- The first paragraph must start with "This PR". Use imperative present tense.
- Include motivation, and contrast with previous behaviour where relevant.
- Do NOT use markdown headings (## Summary, ## Test plan, etc.) in PR bodies.
- Include the full Rust name of each function the PR concerns (e.g.
  `rmcp::model::request_state::RequestStateCodec::open_rs1_at`) so that automation can find it.
- State the commands run on the head commit and their results.

**Footer format:** a footer is mandatory and must contain:

- **Breaking changes (if any):** changes to a signed-off specification, `Defs` definition, axiom,
  exclusion, or theorem name, each with justification and the consumers it affects.
- **Trust changes (if any):** every axiom, patch, `exclude`, or `opaque` entry added, removed, or
  changed, and every `#guard_msgs` axiom list that changed.
- **AI disclosure:** one line per AI-drafted or AI-reviewed artifact; see
  [AI contributions](#ai-contributions).
- **Referencing issues:** closed issues on a separate line prefixed with `Closes`, e.g.
  `Closes #123, #456`.

**Labels:** PRs are encouraged, but not required, to use the same labels as the issues they close.

## External functions and axioms

Aeneas translates only the crate. Everything it calls from outside (the opaque
`request_state_wire::prim` functions, `now_ms`, standard-library operations without an Aeneas
model) is declared by hand in `formal/trusted/Rmcp/FunsExternal.lean` (types in
`TypesExternal.lean`), following plan Section 4.

- **Never a bare `Result` axiom.** Do not write `axiom f : … → Result T`; it asserts nothing
  returns, so proofs through it get stuck. Give an exact model as a definition, or `ok` of an
  opaque value: `def hmac_sha256 k m := ok (hmacSha256 k m)` with `opaque hmacSha256`.
- **No axioms in `trusted/`** (human decision 2026-11-23). Every external is a definition or a
  `structure`; what cannot be computed is an `opaque` constant (`hmacSha256`, `sipHash13`,
  `nowMs`, `SerdeJsonErrorImpl`), which adds no axiom. Laws such as `b64Decode (b64 x) = some x`
  are theorems in `formal/proofs/Proofs/External/`, and `trusted/axioms.lock` stays empty. Adding
  an axiom again is a human decision.
- **No axioms on merged types.** Do not axiomatise a function whose Lean type merges distinct Rust
  types (for example `size_of`); state the fact as a hypothesis on the spec instead.
- **Justify and record.** Each model's docstring cites the Rust source it encodes (pinned crate
  or `rust-src` file and lines) and states its exceptions (panics or behaviour it does not model).
  The same entry appears in the trusted-base section of `formal/docs/STATUS.md`, and
  `formal/trusted/evidence/README.md` names the backing tests (and the differential check in
  `formal/trusted/evidence/differential/`).
- **Consistency.** Not needed while `trusted/` declares no axiom (a definition cannot prove
  `False`); an axiom added later needs a model in `formal/proofs/Proofs/Consistency/`.
- **Visible in specs.** Every spec file lists the axioms of each statement with `#print axioms`
  under `#guard_msgs`. A proof that starts using a new axiom fails the build, so the change must
  appear as a diff of the spec file and in the PR footer. These lists, and `axioms.lock`, show
  axioms only: the external models (definitions, structures, `opaque` constants) do not appear
  there, so a change to a model is caught only by review of `formal/trusted/`; a proof may use a
  model once S08/S09 are signed off (a hash lock over the declarations of `RmcpExternal` is an
  option for the human at that sign-off).
- **`sorry`.** Never merged. A statement whose proof is not finished stays in
  `formal/specs/Drafts/`; open an issue for it.
- **Compiler-trusting tactics.** `native_decide` and `bv_decide` may be used while developing a
  proof, never in a merged one: `lean-guard.sh sources` rejects both words, and the axioms they
  add fail the `axioms` audit and the `#guard_msgs` checks. The one exception is generated code:
  Aeneas `toStr` proves each string literal's length bound with `decide +native`, and the audit
  accepts exactly those native axioms (statement `decide (<literal>.toByteArray.size ≤ U32.max) =
  true`) declared in the generated `Rmcp.Types`/`Rmcp.Funs`; each one that a
  `Defs`/`Proofs`/`Specs` constant depends on must be listed with a pinned statement in
  `formal/trusted/native-axioms.lock` (human decision 2026-11-22, as in the SPQR project; lock
  scope as in the `axioms` bullet). A new string literal in a target needs a
  reviewed lock entry once some `Defs`/`Proofs`/`Specs` constant depends on its native axiom; the
  check applies once a `Defs`/`Proofs`/`Specs` module imports `Rmcp.Funs` (S06) or `Rmcp` becomes
  a default target. The `toStr` form
  and the `Rmcp.Types`/`Rmcp.Funs` module are required of every such axiom, used or not.

## Review and sign-off

Specifications, `Defs` definitions, axioms, patches, and `exclude`/`opaque` entries are all part of
what must be trusted. Each one gets:

1. **at least two independent agent reviews** (`mcp-review`, in separate sessions, with no access
   to each other's reports), using the [AI review questions](AI_PR_REVIEW_QUESTIONS.md), recorded
   in `spec_reviews` of the function record or in the evidence file; then
2. **sign-off by the named human spec owner**, using the [reviewer guide](REVIEWER_GUIDE.md).

Agent agreement alone never accepts anything. Proofs need no separate trust review: Lean checks
them. They are reviewed for style, layering, and build time.

## Performance

All PRs are expected to consider their impact on verification and CI time. Report the build time
of changed proof files in the PR body when it exceeds a few seconds, and justify regressions.

## AI contributions

AI tools, including the Claude agent roles of plan Section 10, may draft specifications, proofs,
axioms, patches, tests, and records, and may review them. The human submitting the PR is
responsible for all of its contents.

### Specifications

AI-drafted specifications are allowed, under these conditions:

1. **Disclosure.** The PR footer lists each AI-drafted artifact, for example
   `AI-drafted: open_rs2_at_spec statement; Base64 model in FunsExternal.lean`. Record the tool and
   model in the step's evidence file and in `spec_drafted_by`.
2. **Grounding.** Each drafted clause cites the Rust lines at the pinned commit, or the section of
   plan Section 3 or 4, that it encodes. A clause with no source is a defect, not a design choice.
3. **No self-acceptance.** An AI may not set `spec: REVIEWED`, mark a task `ACCEPTED`, or approve
   a PR. Every AI-drafted specification gets the independent reviews and human sign-off of
   [Review and sign-off](#review-and-sign-off) before any proof of it starts.
4. **Separation of roles.** The agent that drafted a specification may not prove it, and may not be
   one of its reviewers. A proof worker that finds a signed-off specification false returns a
   counterexample; it does not weaken the statement, and the spec returns to `DRAFT`.
5. **Axioms, patches, and exclusions.** AI-drafted axioms, external models, patches, and Charon
   setting changes follow the same rules, and each needs explicit approval from the spec owner in
   the PR review.

### Specifications before proofs

A specification is signed off before it is proved (`VERIFICATION.md` §6). A PR may contain both
only if the specification was signed off in an earlier review round on that PR, and was not changed
afterwards to make the proof go through. Any change to a signed-off statement re-opens its review.

### Proofs

AI-generated proofs are welcome if they comply with the [style guide](STYLE_GUIDE.md) and this
document. In phase B any working proof is acceptable; refinement waits for phase C. The proof
worker edits only its assigned file under `formal/proofs/Proofs/` and the statement's restated theorem
entry in the spec file. It may not change statements, `Defs`, generated files, or anything under
`formal/trusted/`, and may not add axioms, `sorry`, `native_decide`, or `bv_decide`.

### Authorship

AI tools are never listed as authors in Lean file headers; see the
[style guide](STYLE_GUIDE.md#header-and-imports). Use the commit trailer convention of the
repository for attribution.
